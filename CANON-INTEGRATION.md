# Combining the Illuminated Manuscript with the full corpus

> Meant to be run locally in Claude Code. Every step below is a command or edit you make in
> your own checkout — there is no round-trip back to v0. See `CLAUDE.md` for project context.

This project is two separable layers:

1. **The design system** — `manuscript-ds/` (theme + primitives). Content-agnostic; never touch it to add sources.
2. **The Canon application** — `app/canon/*`, `components/canon/*`, and the data in `lib/canon-data.ts`, generated by `scripts/parse-canon.mjs`.

Merging the full corpus is a **data-layer** task. The theme and the pages stay as-is; you only regenerate the data.

## The one file that matters: `scripts/parse-canon.mjs`

It turns the raw markdown export into `lib/canon-data.ts`. It is format-driven — it discovers every `# Part N:` section and every `**Author · Year**` anchor — so **adding more sources needs no code change**, as long as the full export keeps the same shape as the lite edition:

```
# Part 1: The Title of the Part
...
# The Title of a Source
**Author Name · 2024**
<span class="src">https://example.com</span>
> *One-line lead.*
> - A summary bullet
> - Another bullet
```

## Step 1 — More sources (metadata + summaries)

This is the lean path and what the app already expects.

```bash
node scripts/parse-canon.mjs path/to/full-corpus.md
```

Regenerates `lib/canon-data.ts` with every source. The contents page, folio reader, search, and chronology all scale automatically. Nothing else to do.

## Step 2 — Full body text

Full bodies are large (the lite edition dropped ~19MB of them). Do **not** inline them into `lib/canon-data.ts` — that would ship a giant JS module to the browser. Instead extract them as separate files and load them on demand:

```bash
node scripts/parse-canon.mjs path/to/full-corpus.md --with-body
```

This writes:
- `lib/canon-data.ts` — the lean index, now with `bodyPath` and `wordCount` per entry.
- `content/canon/<slug>.md` — one markdown file per source's full text.

### Wiring the body into the folio reader

The folio reader (`app/canon/[slug]/page.tsx`) is a Server Component, so it can read the body file at request time. Sketch:

```ts
import { readFile } from "node:fs/promises"
import path from "node:path"

async function loadBody(bodyPath: string) {
  const file = path.join(process.cwd(), "content", bodyPath.replace(/^canon\//, "canon/"))
  try {
    return await readFile(file, "utf8")
  } catch {
    return null
  }
}
```

Render it below the existing "Illuminations" summary, ideally inside a `<FolioProse>` so it inherits the drop-cap and serif measure. Add a markdown renderer (e.g. `react-markdown`) if the bodies contain formatting you want to preserve.

### If you'd rather use a database

For full-text search across complete bodies, or if the corpus grows beyond what the filesystem should hold, move `content/canon/*` into a database (the recommended default here is Neon Postgres) and query per-slug in the reader. The in-memory substring search on the contents page is fine for summaries but is not a full-text index — swap it for a real index (Postgres full-text, or a search service) once you index bodies.

## What NOT to change

- `manuscript-ds/` — the portable theme. Reuse `Folio`, `FolioProse`, `InstrumentPanel`, `InstrumentSearch`, etc. as-is.
- The page layouts — they read from `lib/canon-data.ts` generically.

## Regenerating from scratch (checklist)

1. Drop the full export somewhere (e.g. `scripts/canon-source.md`).
2. `node scripts/parse-canon.mjs scripts/canon-source.md --with-body`
3. Wire `bodyPath` into `app/canon/[slug]/page.tsx` (Step 2 above).
4. Run the app; the parser prints entry counts and any missing `src`/bullets to verify the export parsed cleanly.
